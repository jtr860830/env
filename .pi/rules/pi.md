## pi

pi (`brew "pi-coding-agent"`, 1.5.0) has no XDG handling: `dist/config.js` builds every path from `join(homedir(), ".pi", "agent")` unless `PI_CODING_AGENT_DIR` is set, and upstream closed the XDG request as wontfix ([earendil-works/pi#2870](https://github.com/earendil-works/pi/issues/2870)), so the two variables in `env.fish` are the permanent answer — `PI_CODING_AGENT_DIR=$XDG_CONFIG_HOME/pi` (settings, models, `auth.json`, prompts, themes) and `PI_CODING_AGENT_SESSION_DIR=$XDG_DATA_HOME/pi/sessions`. Sessions go to DATA, not STATE. The spec's STATE is for what is "not important or portable enough to the user" for DATA — "actions history" and undo history are its examples — and pi treats sessions as the opposite: never pruned (no retention setting exists; `PI_CACHE_RETENTION` is provider prompt caching), compaction keeps the original entries, abandoned branches survive, and sessions are named, searched, forked, cloned, exported and shared (`docs/sessions.md`). STATE was the first choice, reasoned from the "actions history" example alone; a cold question to Codex and then pi's own docs both pointed to DATA, and OpenCode keeps its sessions there too. Verified on first run: `auth.json` and `models-store.json` landed in `~/.config/pi`, and `~/.pi` was never created. Its `fd`/`rg` downloader checks `PATH` first, so with both in the brewfile nothing is downloaded into the agent dir's `bin/`. Like the Go variables, these reach only processes started from fish.

`settings.json` stays local for the same reason as Claude's and Codex's: pi writes it itself (`writeFileSync`, so a stowed link would survive, but the writes would land in this public repo), including a `deviceId` that regenerates when removed, a `lastChangelogVersion` that changes on every upgrade, and the `packages` list `pi install` maintains. Its hand-set values are listed under `## Manual Setup`: `shellPath` (pi's `bash` tool otherwise runs `/bin/bash` 3.2, and models routinely write bash 4+ — `brew "bash"` is in the brewfile for that; verified `$BASH_VERSION` 5.3), `defaultProvider`/`defaultModel`, and `modelThinkingLevels`. `auth.json` and `trust.json` are credentials and a per-directory decision, also local.

### pi is the harness; Claude Code and Codex are backends (decided 2026-11-10)

The orchestrator runs in pi on `anthropic/claude-fable-5-2` (company API key, `auth.json`; 5.2 appeared in the catalog on 2026-11-11 at $8/$40 against 5.1's $10/$50, otherwise identical). When that credit runs out the user switches by hand with `/model` to `claude-code/claude-fable-5-2` — the Claude subscription through the `pi-claude-code` package — and types "continue". An extension that did the switch automatically was written, tested with a bogus key, and removed the same day: the orchestrator always has a person in front of it, and 40 lines whose trigger text had never been seen for real were not worth keeping. OpenAI models use the ChatGPT subscription (`/login openai`, `openai` provider, `oauth` in `auth.json`); the old `openai-codex` provider is legacy and not used. Codex CLI itself has no role in pi.

**`pi-claude-code` over `pi-claude-bridge`.** Both use the Claude subscription through the `claude` binary. The bridge (elidickinson) runs Claude Code through the Agent SDK with Claude Code's own system prompt in front and pi's prompt as appended sections, loads `~/.claude` settings and hooks, and mirrors pi's history into Claude Code session files — faithful to Claude Code, which is exactly what pi was adopted to escape. The official one (earendil-works) runs `claude -p --system-prompt-file <pi's prompt> --tools "" --setting-sources "" --strict-mcp-config --disable-slash-commands --max-turns 1 --no-session-persistence` with `CLAUDE_CODE_DISABLE_AUTO_MEMORY`, `CLAUDE_CODE_DISABLE_CLAUDE_MDS`, `DISABLE_AUTO_COMPACT`, `ENABLE_TOOL_SEARCH=false` and telemetry off, through a loopback relay that rebuilds every user message from pi's history and strips Claude Code's reminders. Measured on 2026-11-10 by pointing `ANTHROPIC_BASE_URL` at a local capture server and running `claude` 2.1.311 with that argument set: the `system` array is three blocks — a one-line `x-anthropic-billing-header`, the sentence "You are a Claude agent, built on Anthropic's Claude Agent SDK.", and pi's prompt verbatim — plus one `role: system` message of about 250 tokens (cwd, platform, OS, a note on untrusted downloads, model name and cutoff, date) that the relay keeps in a stable position; `tools` is empty. The `<system-reminder>` with the account email that Claude Code adds to the first user message is what the relay removes. So the subscription path costs one sentence and one small fixed message over the API path. Its usage-credit guard reads `rate_limit_event.isUsingOverage` and fails the turn rather than paying extra usage. pi's own `/login anthropic` OAuth is not used: pi's code says third-party harness usage under subscription auth "draws from extra usage and is billed per token", so it has no advantage over the API key.

### Subagents

`config/pi/.config/pi/extensions/subagent/` is the official example (`examples/extensions/subagent/`, ~1,000 lines) kept as a file the user can read whole, rather than `tintinweb/pi-subagents` (~70,000 lines, background jobs, worktrees, scheduling, agent memory). What was added, each tested with headless `pi -p -a --mode json` runs and one tmux-driven TUI run on 2026-11-10/11:

- frontmatter `thinking:` and a per-task `thinking` parameter (call > agent file > inherited); without it an agent that pins a model gets pi's default level, because the example only forwards `--thinking` when the model is inherited.
- a per-task `model` override — one `reviewer` file dispatched twice, once with `model: openai/gpt-6-astra`, is the cross-family review; a second agent file with an identical body was the first design and was dropped as duplication.
- frontmatter `fallback: [...]`, tried in order when a child exits with a quota error (`usage limit|credit balance|billing|insufficient_quota|out of budget|quota exceeded|available balance|spend limit`, pi's own non-retryable list plus the two vendors' wording). Other errors do not switch models — pi's child already retries transient ones — and a `model` override disables the chain, since falling from Astra to Opus would make the second reviewer the same family as the first. The result names the model it ran on and the ones that failed.
- `background: true`: the tool returns a job id at once; the result arrives as a `subagent-result` custom message via `pi.sendMessage(..., { deliverAs: "followUp", triggerTurn: true })`, which wakes an idle orchestrator or waits for the current turn; `/subagents` lists and kills; `session_shutdown` aborts running jobs. Without a UI (`-p` mode) `background` is ignored and the call runs in the foreground, because pi exits when the agent settles and would kill the job. A `subagent_wait` tool existed for a day and was removed on 2026-11-11: blocking on a background job is the foreground mode, and while it waited the user's input sat in the steering queue unseen — ending the turn and letting the result wake the orchestrator gives the same sequence and keeps the user able to talk. Escape does not kill background jobs on purpose: stopping the orchestrator mid-thought should not throw away a worker's five minutes.
- child identity: the spawn sets `PI_SUBAGENT=<agent>`, the extension registers nothing when it sees that variable, and the appended system prompt ends with a paragraph saying the process is a subagent that cannot delegate. Without this a full-tool worker had the `subagent` tool and the orchestrator instructions from `~/.config/pi/AGENTS.md`, verified by asking a child to list its tools.
- `--no-session` removed, so a child's session can be resumed and read afterwards. Sessions are flat under `PI_CODING_AGENT_SESSION_DIR`.
- the tool description is built at registration from the user-level agent files, listing name and description — that list is how the orchestrator chooses, so an agent's `description` is its routing rule and says what it is for and what it is not for.

Agents are bundles of defaults (model, tools, fallback, report format), not roles; the role goes in the brief. Six cover the grid of model tier × tool set: `scout` (read-only on disk, terra), `researcher` (read + `web_search` + `fetch_content` from pi-web-access, sol with `thinking: high` pinned, because synthesis is where research quality lives and the input-heavy fetching step gains nothing from a bigger model; pass `model: openai/gpt-6-astra` for decision-critical research), `tester` (read + bash, luna), `worker` (full, sol), `expert` (full, astra), `reviewer` (read-only, Claude Opus — a different family from the workers by design). `expert` and `reviewer` also pin `thinking: high` in the file (2026-11-11): their models are `high` in the local `modelThinkingLevels` anyway, but that table is not in the repo and does not cover a `model` override to something it does not list, and depth is part of what those two are for. `scout`, `tester` and `worker` leave it to the table. Descriptions and bodies are written as capabilities with coding as one example, not as engineering roles: the example's wording (`codebase`, `Key Code`, `git diff` first) made the orchestrator hesitate to send a document or a plan to `scout` or `reviewer`. `--tools` can name extension tools such as `web_search` directly; pi-web-access's `web_enable` indirection is only for the default declaration. OpenAI first for execution because that subscription is the user's own and Claude is the company's; fallbacks go OpenAI → Anthropic API → Claude Code subscription. `planner` was dropped (the orchestrator is the strongest planner available), `worker-heavy` was renamed `expert`, and the example's three workflow prompts were deleted: process (explore → implement → test → review, when to escalate, when to double-review) belongs to skills such as mattpocock/skills `grill-me`, Google's EGM or obra/superpowers, all of which have pi install paths, not to the mechanism. Designs considered and rejected the same day, all for replacing the orchestrator's judgement with a mechanism: a Luna classifier choosing worker vs expert, automatic escalation on a `STATUS: failed` line, tmux panes per subagent (observation is already in the parent TUI, and steering a subagent would bypass the orchestrator).

`~/.config/pi/AGENTS.md` (stowed) is the user-level context file: the language rule and a short Orchestration section. It loads in subagent children too, which is why the identity paragraph exists.

### Rules and skills for pi

pi has no path-scoped rules. `.pi/extensions/rules.ts` reproduces Claude Code's `paths` frontmatter: at `session_start` it walks up from cwd to the first directory holding `.pi/rules`, parses each file's `paths` globs (own glob→regex, no `minimatch` for extensions; a trailing `**` must become `.*`, the first version matched nothing), and on `read`/`edit`/`write` of a matching path injects the rule once per session as a `rule` custom message. `edit`/`write` are blocked the first time with a reason telling the model the rule is already in context — the first wording, "Read it, then retry", made the model `read` the file as well, doubling the tokens. Resume re-reads injected ids from the branch; `fs.watch` on the rule directory reloads on change and re-arms only the rules whose body changed. **All rules hit by one tool batch go out as one message**, flushed with `setTimeout(0)` after the batch's `tool_call` preflights. The first version sent one message per rule, and pi's default `steeringMode: "one-at-a-time"` delivers queued steer messages one per turn — so a scout whose spot-check batch read fish, ghostty and tmux config got one rule with the tool results, wrote its report, and then received the other three one turn at a time, answering each with "Noted; this tmux rule was included in the audit." The subagent tool takes the last assistant text, so the orchestrator saw "Noted" and not the 5,000-character report that was two messages earlier. It happened twice with terra and not with sol only because of where the spot-check landed in the sequence; the session files under `PI_CODING_AGENT_SESSION_DIR` are what made the cause visible. Skills in `.pi/skills/` are discovered by pi natively. Both directories were `.claude/rules/` and `.claude/skills/` until 2026-11-11, read by pi through a `RULE_DIRS` entry and a `.pi/settings.json` pointing `skills` at `../.claude/skills`; they moved once pi was the only harness used here, so Claude Code no longer sees them in this repo. Project resources under `.pi/` need project trust: `-p` cannot ask, so the first two headless tests ran without the extension while the model reported rules "loaded" from the table in `AGENTS.md`; `trust.json` now holds the decision and `pi -p -a` approves for one run.
