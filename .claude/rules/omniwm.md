## OmniWM

Tiling window manager (cask `omniwm`, 0.8.0, settings schema 5). `config/omniwm/.config/omniwm/settings.toml` is stowed: OmniWM live-reloads it on every save and writes Settings-window changes back **through the symlink** — verified both ways, the link survived a GUI save and the edit landed in the repo. Runtime state (window placements, clipboard) lives in `~/.local/state/omniwm`, not in this file. The schema is strict: change values in place, never delete keys — a missing key rejects the whole file (OmniWM then keeps the previous settings; 0.8.0 also shows a notice on screen). The docs mark only `[windowSwitcher]`, `[keyboardModes]` and `[island]` as optional tables, and the GUI rewrites the whole file in its own order on every save, so a deleted line comes back anyway. It drops comments when it rewrites, which matches this repo's no-comment rule.

**The 0.7.6 → 0.8.0 upgrade (2026-11-10) rewrote the file once**: schema 4 → 5, the five top-level `monitor*Overrides = []` lines gone, every new key written at its default, and the six resize-span hotkeys renamed from `setContainerPrimarySpan.decrease10Percent`-style ids to `resizeContainerPrimarySpan.shrink` / `.grow` with their bindings kept (`⌥-`/`⌥=` for the column, `⌥⇧-`/`⌥⇧=` for the window's secondary span). The upgrade writes a `settings.toml.pre-v5` backup beside the target; it was deleted, so 0.7.6's file is only in git history, and 0.7.6 cannot load a schema 5 file. Settings pages were renamed: Hotkeys → Keyboard Shortcuts, Monitors → Displays, Workspace Bar → Styles & Widgets, gaps moved to Layouts → Spacing, borders to Appearance → Window Borders.

### Layout and workspaces

Layout follows how the machine is used — one window fills each screen. Workspaces 1–3 live on the built-in display (1 Ghostty, 2 Zen, 3 for anything else) and 4–5 on the secondary display. There is no way to make a workspace exist only while its display is connected: when the home display is missing, OmniWM places the workspace on the nearest connected one (`effectiveMonitor` in `WorkspaceManager+MonitorResolution.swift` in 0.7.6; `specificDisplay` assignments fall back the same way), so unplugged, 4 and 5 join the built-in display — read from source, not yet observed. Splitting the numbers per display keeps the built-in set stable either way, and `workspaceBar.hideEmptyWorkspaces = true` hides any inactive empty workspace from the bar and Overview and makes next/previous navigation (the three-finger swipe) skip it — so an unplugged 4–5 with nothing in them stays out of sight. `⌥1-5` and `⌥⇧1-5` still reach empty workspaces; only drag-and-drop onto one is lost, since it is no longer drawn. Niri with `visibleContainerCount = 1` and `defaultContainerPrimarySpan = 1.0`, so every column is full width; `⌥.`/`⌥,` cycle a column through ⅓/½/⅔ for a side-by-side view and `⌥⇧F` toggles full width back. `edgeGaps = false` and `gaps.size = 8`, otherwise a full-width column is inset 16pt on every side once a workspace holds two windows. The focus border is off: with one window per screen it marked nothing and cost 5pt on each edge.

Each workspace's `displayName` is its number — `"1"` to `"5"`, the same as `name` — since 2026-11-10. They were `Term`, `Web`, `Etc`, `Ref`, `Etc` before; two findings from then still hold: `displayName` need not be unique (0.7.6 accepted the duplicate, and every `switch-workspace` form takes a number, never a display name), and Nerd Font glyphs do not work as names — the bar and menu bar render in the system font, and CoreText resolves U+E795 to `LastResort`, the boxed question mark (`swift` with `CTFontCreateForString` is the instrument). `general.workspaceAutoBackAndForth` (new in 0.8.0, i3's `workspace_auto_back_and_forth`) stays `false`.

**`niri.infiniteLoop = true` wraps keyboard navigation only.** `⌥←→` past the last column returns to the first. The three-finger column scroll does not wrap, by construction rather than by bug: in 0.8.0 the setting's one consumer is `NiriLayoutEngine.wrapIndex`, which `NiriNavigation.swift` and `ColumnConsumption` call to take an index modulo the count, while the trackpad path (`applyTrackpadViewportScrollDelta` → the animation driver → `endProjectedGesture` → `NiriGestureSnapPlan`) drags a bounded strip and clamps the result to `0 ... count - 1`; its only edge behaviour is `allowOverscroll`, which stays `false`. Nobody has filed this upstream; the nearest issue, #686, asked for wraparound inside a tabbed column and was closed Not Planned (coupling with cross-monitor focus edges). The three-finger workspace swipe wraps through `gestures.workspaceSwipeEdgeBehavior = "cycle"` (new in 0.8.0, trackpad only; the hotkeys always wrap).

`assignToWorkspace` rules route Ghostty to 1 and Zen to 2, but only for an app's **first** tracked window — later windows open on whatever workspace is active. Keeping workspace 1 terminal-only would need a `omniwmctl watch windows-changed` guard; declined for now.

**Everything else tiles on workspace 3.** A last rule with an empty `bundleId`, `titleRegex = ".*"`, `assignToWorkspace = "3"` and `layout = "tile"` sends any app without its own rule to the built-in display's catch-all as a full-width column. 3 rather than 5 because it exists with or without the secondary display, and a rule names one workspace. It replaced a catch-all `layout = "float"`, which kept ad-hoc windows from pushing the tiled one aside but left them loose on whatever workspace was active. The rule works through specificity (`AppRule.specificity` in 0.7.6: bundle ID +2, each other matcher +1), resolved **per setting**: Ghostty's and Zen's rules (2) win, but only for settings they set, so both carry an explicit `assignToWorkspace` and `layout`. 0.8.0's release notes say a rule that used to lose to a more specific one now applies the settings it sets — the same per-setting model this file already assumed, so nothing changed here. A window with no AX title fails the regex (`guard let title … else { return false }`) and tiles on the active workspace. Verified with TextEdit: it opened as a column on 3 while Ghostty stayed on 1. Limits observed: `assignToWorkspace` moves only an app's first tracked window, so a second window of the same app becomes a column on the active workspace — send it on with `⌥⇧3`; and Calculator, a fixed-size window, appeared on no workspace at all once the rule said `tile` (it floated at 230×408 under the old rule) — cause not read from source, so a non-resizable tool that misbehaves needs its own `layout = "float"` rule. `⌥⇧Space` toggles `toggleFocusedWindowFloating` for one window (unassigned by default; the i3/sway `mod+shift+space` convention, and free among the bound chords — plain `⌥Space` types a no-break space in macOS text fields).

**A floating window belongs to the workspace it opened on — there is no sticky / all-workspaces window.** The 0.7.6 source sets `canJoinAllSpaces` only on OmniWM's own panels (workspace bar, Quake, tooltips), app rules can set layout, workspace, minimum size and initial span but nothing like "every workspace", and OmniWM workspaces are not macOS Spaces (off-workspace windows are parked off-screen), so the native "assign to all desktops" does not apply either. The only thing that follows workspace switches is a revealed scratchpad; auto-assigning new floating windows into one with a `omniwmctl watch windows-changed` launchd agent was weighed and declined — every ad-hoc window would share one slot, `scratchpad assign` acts on whichever window has focus, and assignments vanish on restart. Move a float with `⌥⇧1-3` instead. Scratchpads were considered for summon-on-demand apps; their membership lasts only for the OmniWM process (labels persist, assignments do not), so they need re-assigning after every restart and are unused for now.

### Workspace bar: three layers, `settings.toml` at the bottom

0.8.0 replaced the fixed bar with OmniShell — Luau widgets drawn by a *style*. The bar's configuration now resolves in this order, highest first:

1. the user's profile, `~/.config/omniwm/shell/shell.toml`, section `[profiles.default.workspaceBar]` — **not stowed, not in this repo** (decision still open; it is the file Settings → Styles & Widgets → Bar writes to, and OmniWM re-sorts it on save);
2. the style's own file, `~/.config/omniwm/shell/default/shell.toml`, which OmniWM overwrites on every update (Default: 32pt, full width, over the menu bar, reserving layout space, `backgroundOpacity = 0`, `showItemBackgrounds = false`, a System Stats button);
3. `settings.toml`'s `[workspaceBar]`, which only decides keys neither layer above sets.

Verified: `settings.toml` says `height = 24`, Default says 32, `omniwmctl query workspace-bar` reported 32 until the profile set 24. The docs promise only that `enabled`, `excludedBundleIDs` and `iconOverrides` stay global; in practice the keys `settings.toml` still owns here are `hideEmptyWorkspaces`, `revealModifier`, `revealHoldMilliseconds`, the autoHide delays, `hoverPreviewsEnabled`, `deduplicateAppIcons`, `showFloatingWindows`, `notificationBadges`, `hideInNativeFullscreen` and `notchActiveZoneWidth`. The profile currently holds, and must keep, these so the bar looks as it did under 0.7.6:

```toml
[profiles.default]
center = ["workspaces", "scratchpads"]
leading = []
trailing = []

[profiles.default.workspaceBar]
autoHide = true
fullWidth = false
height = 24
notchMode = "moveBelowMenuBar"
position = "overlappingMenuBar"
reserveLayoutSpace = false
windowLevel = "popup"
```

Why each: `autoHide = true` is required for the ⌥ reveal — 0.8.0's `revealModifier` only reveals bars whose resolved `autoHide` is true, where 0.7.6 hid a bar on the modifier alone; `fullWidth = false` because an enabled full-width bar anywhere but Below Menu Bar sets macOS's "Automatically hide and show the menu bar" to Always (it restores the old value on a normal quit, a crash can leave it set — check `defaults read NSGlobalDomain _HIHideMenuBar`); `windowLevel = "popup"` because the names map to NSWindow levels (normal 0, floating 3, menu bar 24, status 25, popup 101) and the GUI's `normal` would sit under the menu bar on the notch-less external display, where Overlapping Menu Bar really overlaps — on the built-in display `notchMode = "moveBelowMenuBar"` moves the bar below the menu bar instead; `reserveLayoutSpace = false` is moot (auto-hidden bars never reserve) but kept explicit. Default's `backgroundOpacity = 0` and `showItemBackgrounds = false` were left in force, so the bar is more transparent and has no pill backgrounds compared with 0.7.6 (0.1 and true). Everything else under `~/.config/omniwm/shell/` — `default/`, `omniwm.d.luau`, `.luaurc`, `themes/wallpaper.toml` (generated when the wallpaper palette is previewed) — is app-owned and stays out of the repo. Bottom placement was tried and dropped on the way: it shares its reveal edge with the auto-hidden Dock. The bar's leading OmniWM button of 0.7.6 is gone with the fixed bar; the `omniwm` widget is simply not in any lane.

The menu bar item shows only the active workspace's number (`statusBar`: `showIcon = false` since 2026-11-10, `showWorkspaceName = true`, `useWorkspaceId = true`). Its dropdown is trimmed by `[statusMenu]` (new in 0.8.0): every control tile hidden, the help card and Check for Updates and Hidden Icons rows off — the tiles were toggles for things this file decides (borders, Hidden Bar, focus-follows-mouse…), and a GUI toggle writes straight into the repo, which is how Hidden Bar was once switched on without anyone deciding to (it rode along in 2140bd4 until noticed on 2026-11-02). **Read the whole `settings.toml` diff before committing any OmniWM change**, since the file can carry GUI edits made since the last commit.

**Hidden Bar is off** (`hiddenBar.enabled = false`, also in the profile). It conceals menu-bar icons, but only with Full Disk Access granted to OmniWM and only while the workspace bar is on; it had nothing selected and no such permission, so it did nothing. If the notch ever starts swallowing menu-bar icons, a standalone tool (OmniWM's docs point to Thaw) is the better trade than giving the window manager Full Disk Access.

### Window switcher

`[windowSwitcher] enabled = true` since 2026-11-10 (new in 0.8.0): `⌘Tab` cycles the active workspace's windows with thumbnails, `⌥Tab` all workspaces; `scope = "activeWorkspace"` is the remembered choice for the S key. Thumbnails need Screen Recording and the shortcuts need Input Monitoring. With one window per workspace it mostly duplicates `⌥1-5`, kept because the user likes it.

### Quake, launcher, keyboard modes

**The Quake terminal is off** (`quakeTerminal.enabled = false`, `provider = "ghostty"`). It is OmniWM's embedded libghostty and reads the same Ghostty config files, so Ghostty's `command` — which starts tmux, see `.claude/rules/ghostty.md` — would attach it to the main session as a second client. A shell-side guard was tried first (`$__CFBundleIdentifier` is `com.barut.OmniWM` in a Quake shell, `com.mitchellh.ghostty` in Ghostty) and dropped in favour of keeping tmux out of the shell config entirely. Measured from a Quake shell before it was disabled: `GHOSTTY_BIN_DIR` inside `OmniWM.app`, `TERM_PROGRAM=ghostty`, `TERM_PROGRAM_VERSION=1.3.2-main+…`, `TERM=xterm-256color`. Re-enabling Quake means first giving it a config that does not carry `command`; 0.8.0 also offers `provider = "kitty"` / `"foot"`, neither installed. `[launcher]` (the palette's Applications mode, new in 0.8.0) has no entries — Alfred launches things — and `terminal = "ghostty"` only names where a saved command would run. `[keyboardModes]` is empty and `toggleShortcutPause`, `beginPrefix`, `toggleWindowMode` are unassigned; Pause would hand `⌥←→` back to an app without Input Monitoring, the other two need it. `[island]` and the `shellPermissions.services` (`lyrics`, `weather`, both `true` by default and unused with no widgets) are untouched.

### Overview colours

Only the selected window's border can follow light/dark: with `overview.matchFocusBorder = true` it takes the focus border's colour (`OverviewAppearance` calls `BorderConfig.from(settings:isDark:)`), and `borders` has both `color` (light) and `darkColor` (dark). Those are set to purple — `#a626a4` / `#c678dd`, the colour that means "current" everywhere else (`TabLineSel`, tmux's current window) — while the focus border itself stays disabled; only its colour is borrowed. Backdrop, resting and hovered borders take a single colour for both appearances and stay at OmniWM's defaults: the backdrop is fully transparent, so they are drawn over the wallpaper and a contrast measurement against the palette would not mean anything.

### Gestures and hotkeys

**Trackpad gestures**: three fingers scroll Niri columns left/right and switch workspaces up/down (OmniWM's defaults — the two share a finger count because their axes differ); four fingers swiping up/down open and close Overview. macOS's own three- and four-finger swipes (full-screen apps, Mission Control) are turned off in System Settings, since both would fire on the same swipe. Window move and resize gestures stay off: `GestureSettingsValidation` requires each to have a finger count no other enabled gesture uses, three and four are taken, and two fingers is ordinary scrolling — `⌥`-drag with the mouse or trackpad covers both. 0.8.0 additions left at their defaults: `adoptNativeResize` and `adoptNativeMoveAcrossDisplays` off (a native edge drag on a full-width column should snap back; displays are crossed with `⌥⇧4/5`), `resizePreviewStyle = "live"`, and `focus.edgeNavigationInterval = 1.5` — hovering at a Niri screen edge for that long scrolls the parked neighbour column in, which only arises with two columns side by side; `focus.followsMouseOnlyFullyVisible = true` would switch it off.

Hotkeys stay on OmniWM's `⌥` defaults. They take `⌥←→↑↓` from fish (word motion, token history search) — accepted, since vi mode moves with `w`/`b` — and Hyper was not set up. `updateChecksEnabled = false` (brew updates it) and `ipcEnabled = true` (for `omniwmctl`, protocol 22 in 0.8.0; the bundled CLI matches).

### Manual setup

Grant Accessibility and Input Monitoring on first launch, plus Screen Recording for the window switcher's thumbnails (Input Monitoring also covers its shortcuts). Keep **Displays have separate Spaces** on, and turn on **Start at Login** in OmniWM's menu — it is a macOS login item, not a key in `settings.toml`. Recreate the profile block above in Settings → Styles & Widgets → Bar, or copy it into `~/.config/omniwm/shell/shell.toml`, until that file is stowed.
