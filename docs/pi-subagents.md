## pi subagents

`config/pi/.config/pi/extensions/subagent/` started as the official example (`examples/extensions/subagent/`, ~1,000 lines) kept as files the user can read whole. Since 2026-11-12 it is three files: `index.ts` (1,216 lines), `fallback.ts` (123) and `agents.ts` (119). Community packages were rejected, all observed 2026-11-11: `tintinweb/pi-subagents` is ~70,000 lines (background jobs, worktrees, scheduling, agent memory), lets an agent file's pinned model override the per-call model (issue #182, open since 2026-07-28), which breaks dispatching one reviewer file on two model families, and had 117 open issues; `nicobailon/pi-subagents` removed automatic model fallback on 2026-09-14 (PR #2270: quota failures are returned to the caller) and ships roughly daily, about 55 releases in three months, which conflicts with taking packages unpinned at latest; pi itself ships no subagent feature (README: "skips features like sub-agents and plan mode. Ask Pi to build what you want, or install a package that does it your way"). Why pi is the harness and why the user-level context file holds no delegation policy are in `docs/pi.md`.

### Names

Two words, two things (2026-11-12). A *task* is one dispatched piece of work that is running; a *subagent* is the agent and the child process that carries it out. So the tools are `task` and `task_control`, the command `/task`, the session types `task-result` and `task-record`, and every message says "background task id"; `PI_SUBAGENT`, the virtual model `subagent/<agent>`, the extension directory (also the upstream example's name, easy to compare after a pi upgrade) and the state directory name the agent or the extension and keep the other word. Renaming those to `task` was declined for that reason. Until 2026-11-12 the tools were `subagent` and `subagent_task`, the brief was the parameter `task` and the model-side action was `stop`: a tool called `task` with a parameter `task` used one word for both things, so the parameter became `brief`, and the action became `kill` to match `/task kill`. The command was `/subagents` and the messages said "job" until 2026-11-11: it only ever listed background work, and `task` is the Linux word the owner prefers; singular because pi's own commands are (`/model`, `/session`, `/tree`) and it takes a subcommand the way `git branch` does; `/jobs`, `/tasks` and `/bg` were the alternatives.

### Dispatch: the `task` tool

- Modes: single (`agent` + `brief`) and parallel (`tasks: [{agent, brief}]`, at most 8, 4 at a time). An unknown agent or a malformed call is answered at once and never becomes a task.
- frontmatter `thinking:` and a per-task `thinking` parameter (call > agent file > inherited); without it an agent that pins a model gets pi's default level, because the example only forwards `--thinking` when the model is inherited. The per-task value goes through `parseThinkingLevel` (2026-11-11): `tsc --strict` inferred `unknown` from the `StringEnum` schema, here as in the upstream example's own `agentScope`.
- a per-task `model` override: one `reviewer` file dispatched twice, once with `model: openai/gpt-6-astra`, is the cross-family review; a second agent file with an identical body was the first design and was dropped as duplication. An override names a physical model, so the fallback chain is not used: falling from Astra to Opus would make the second reviewer the same family as the first.
- the tool description is built at registration from the user-level agent files, listing name and description. That list is how the main session chooses, so an agent's `description` is its routing rule and says what it is for and what it is not for.
- the description also states the contract of a background task (2026-11-12): until the result message arrives the caller knows nothing of the result, must not predict it, poll for it or redo the work, and may do other work, answer the user or end its turn; a parallel call is one task whose results arrive together. This says what the mechanism does, as Claude Code's prompt does (Prior art); it is not the "verify the report" reminder that `docs/pi.md` records as declined.

### Execution: always in the background with a UI (decided 2026-11-11)

With a UI every call returns a background task id at once and the child keeps running; without one (`-p`) the call runs in the foreground, because pi exits when the agent settles and would kill the task. The `background` parameter, which the model chose per call until 2026-11-12, is gone.

Why: asked what he does while a subagent runs, the owner said he keeps talking to the main session about the same work or walks away, sometimes starts unrelated work, and does not watch the subagent. A foreground call leaves his input in the steering queue unseen. Context isolation, a different model and parallelism are what a foreground subagent still gives over doing the work in the main session, so foreground was not pointless, only blocking. A `subagent_wait` tool existed for a day and was removed on 2026-11-11 for the same reason: blocking on a background task is the foreground mode. Claude Code forcing the background and Codex's trouble without a wake are under Prior art.

Cost of the change: one short extra request per dispatch, the reply that follows "Started background task" (see Costs).

### Result delivery (decided 2026-11-11)

| Situation | Sent as | Wakes the main session |
|---|---|---|
| task finished or failed | `task-result` message, `deliverAs: "followUp"`, `triggerTurn: true` | yes |
| finished after the owner pressed Escape and before his next input | plain `task-result` message | no |
| `/task kill` | plain `task-result` message: "was stopped by the user before it finished", output so far, session id | no |
| `task_control` `kill` | nothing; the output so far is the tool result | n/a |
| session shut down | nothing; reported at the next `session_start` | no |

- The owner intervening by hand means the model does not start on its own: he is present and has a plan, and the best a wake could produce is "noted", the worst a re-dispatch of what he just killed. Other running tasks still wake the model when they finish, and it sees the kill then.
- Escape still does not kill background tasks, on purpose: stopping the main session mid-thought should not throw away a worker's five minutes. Since 2026-11-12 it also holds wakes: `agent_settled` with `aborted: true` sets the hold and the `input` event clears it. By pi's documentation extension commands do not fire `input`, so `/task kill` leaves the hold in place.
- "Plain" means `pi.sendMessage` without `triggerTurn` while the session is idle; when it is not idle the message waits in a queue that `agent_settled` flushes. Measured on pi 1.5.1 with a scratch extension that logged events and each request's context: idle, such a message is displayed and persisted and no run starts, and the next prompt carries it; while streaming it is appended after the current turn and the model answers it in the same run (it replied "I don't have a specific task tied to…"), which is not what the documentation's "appended after the current turn ends" suggests; `deliverAs: "nextTurn"` starts no run in either state but is neither displayed nor written to the session file until the next user prompt, so quitting first loses it. Hence the queue rather than `nextTurn`.
- Separate calls wake separately and a parallel call wakes once; the description tells the model to choose by that. Declined: merging completions inside a time window (tintinweb 200 ms, nicobailon 150 ms to 1 s; near-simultaneous completions are rare) and grouping whatever one turn dispatched (tintinweb's group join, 30 s after the first completion; it decides for the model what belongs together and adds a timeout).
- Stopping returns a result instead of throwing (2026-11-12): messages, usage and session id survive, and a stopped parallel task reports each member as completed, failed or stopped. Before that an abort rejected the whole call and finished members were lost.

### Control

- `/task` lists the running tasks and their members; `/task kill <id|all>` stops them.
- `task_control` gives the model the same list (`list`) and `kill`, which waits for the child to die and returns its output so far. Added because the owner corrects direction while a task runs and the model otherwise had no way to stop a task whose brief had gone stale; it kills and dispatches again with a new brief, which is what "No resume parameter" below already prescribes. Passing a message to a running child (Codex's `send_message` and `followup_task`) was declined: the child is a one-shot `pi -p` with no channel, and that is a larger mechanism than the need. The description says to use `list` when the user asks about progress, not to poll.
- Task ids come from a counter (2026-11-12); the earlier base-36 millisecond suffix could repeat for two calls in one batch, and the second would have replaced the first in the map. The counter restarts on reload.

### Session records and shutdown

Each background task writes `task-record` entries with `pi.appendEntry` (not part of the model's context) when it starts, when a child's session id is known and when it ends, keyed by id and start time because ids repeat after a reload. `session_shutdown` fires for quit, `/reload`, `/new`, `/resume` and `/fork` and aborts every running task: the extension's task map dies with a reload, and after a switch the result would land in an unrelated session. At `session_start` the branch is scanned for tasks started and not ended; each gets an end record and one plain message lists them with their session ids. Before 2026-11-12 the abort was silent and the transcript still said a result would arrive.

Verified in the TUI: `/reload` with a task running (child gone, one notice, no wake) and quit then reopen (one notice, none on a second reopen). `/new`, `/resume` and `/fork` run the same code and were not tried. Declined: asking before leaving (it is unclear that a quit can be intercepted) and tasks that outlive pi (the owner leaves his seat, not pi; a detached child with results on disk is a different scale of mechanism).

### Fallback: a virtual model inside the child (2026-11-12)

Agent files are unchanged: `model` plus `fallback: [...]` is the chain. In a child (`PI_SUBAGENT` set) the extension registers nothing but `fallback.ts`: a virtual model `subagent/<agent>` whose `route()` returns the first usable model of the chain, and an `agent_before_settle` handler. When the last assistant message is a quota error (`usage limit|credit balance|billing|insufficient_quota|out of budget|quota exceeded|available balance|spend limit`, pi's own non-retryable list plus the two vendors' wording) the handler marks that provider spent, appends a hidden `subagent-fallback` message and returns `continue: true`; the next request goes through `route()` and lands on the next model, in the same process and the same session. Other errors do not switch models; pi already retries transient ones.

- The handler is needed because pi classifies quota errors as non-retryable (`NON_RETRYABLE_PROVIDER_LIMIT_ERROR_PATTERN` in pi-ai's `utils/retry.js`), so `route()` is never called with `reason: "retry"` for them and the run would simply end. `continue: true` alone fails with "agent_before_settle requested continuation without runnable model context"; the appended message is what makes the context runnable.
- Continuing across vendors works because pi-ai's `transform-messages.js` skips assistant messages whose `stopReason` is `error` or `aborted`, drops thinking produced by another model, normalises tool-call ids and synthesises results for orphaned tool calls. The new model loses the old one's reasoning and keeps every tool call, result and visible text.
- Once switched, a child stays on the new model: going back mid-task would lose the prompt cache a second time.
- Spent providers are shared through `$XDG_STATE_HOME/pi/extensions/subagent/exhausted-providers.json` (provider → expiry, 15 minutes). A new child skips a listed provider; after expiry the first child tries again, one failed request of a second or two and no tokens. The lifetime is fixed because the error text carries no reset time, and short because staying on the company's Anthropic key after OpenAI has recovered is the expensive mistake. The key is the provider (it was the model for an hour): the ChatGPT limit is the whole subscription's and Luna and Terra failed together; `anthropic` and `claude-code` are separate. A Claude limit on one model class would skip the others too, but `claude-code` is last in every chain, so that only brings the error forward. Children started together each fail once.
- The local `modelThinkingLevels` table is keyed by physical model and has no entry for `subagent/<agent>`, so `route()` looks the level up itself for the model it returns unless the parent pinned one, which it passes as `PI_SUBAGENT_THINKING`.
- The parent derives what happened from the child's messages: a model whose error is followed by a different model is a fallback, and the result says "ran on X after quota errors on Y". The result carries one session id.
- Tested with real quota errors while the ChatGPT subscription was exhausted (2026-11-12, pi 1.5.1 and 1.5.2): failure on the first request and in mid-task (the next model resumed at the second of three files without re-reading the first), two fallbacks in a row, a chain with nothing left (the exit code is still 0, so failure is judged by `stopReason`), the shared file (skip, expiry, two writers), thinking levels from the table and pinned, and an override failing outright. First real exhaustion was 2026-11-11 ("has reached their Subscription Sharing usage limit", caught by `usage limit`).
- Until 2026-11-12 the parent ran the chain: a child that exited on a quota error was started again from the brief on the next model. On 2026-11-11 a researcher lost 15 minutes and 30 turns on `gpt-6.1-sol` that way and the rerun on Sonnet took 8 minutes, 36 turns and $1.47.
- Declined: the parent restarting the child with `--session <id>` and a "continue" prompt. It was verified first on a real sample (a session that had failed after 4 turns with OpenAI encrypted thinking and parallel tool calls continued on `anthropic/claude-sonnet-5-5`: 56,225 cache-write tokens, $0.149, and the model correctly listed its task, the sources it held and its next steps), but it loses in-process state and keeps model routing inside the subagent mechanism. A separate extension with tier names (`tier/sol`) was declined because the agent files are already the one place the chains are written. Using virtual models instead of subagents was declined: a virtual model changes who answers inside one context and gives no isolation, parallelism or separate tool set. Fallback for the main session was considered and declined the same day: it would need its own chain, a changed `defaultModel`, and a rule for long sessions (returning to the first model costs a cache rewrite, about $2 at 210K tokens), while switching by hand is rare and the owner is present; registering the virtual model in the parent too is the small change if that is ever wanted.

### Child identity and sessions

- The spawn sets `PI_SUBAGENT=<agent>`; the extension then registers only the fallback, and the appended system prompt ends with a paragraph saying the process is the named subagent of another pi session that reads its final message, that it cannot delegate because the task tool is not available, and to do the task itself. Without this a full-tool worker had the delegation tool, and until 2026-11-11 the orchestrator instructions from `~/.config/pi/AGENTS.md`, verified by asking a child to list its tools.
- `--no-session` was removed, so a child's session can be read and resumed afterwards. Sessions are flat under `PI_CODING_AGENT_SESSION_DIR`. The extension reads the `id` of the child's first JSON event (`type: "session"`) and ends each result with a line `session: <id>`; with no session event the line is omitted. The transcript opens with `pi --session <id>`, or find `*_<id>.jsonl` under the session directory. The whole id is shown; cutting it to eight characters was considered and left.

### What the owner sees (2026-11-12)

- A widget line per task and, for a parallel task, per member; a finished member stays as `✓ … done` until its group ends. A one-second timer keeps the elapsed time moving; before, the line changed only on child events and looked stuck during a long tool call. The model is blank until the child's first message, because the first choice may be skipped. One line per member was the owner's choice over one line per group; eight members take eight lines.
- A `task-result` message with details is rendered folded, with the collapsed and expanded views the tool block had (Ctrl+O). Notices without details use pi's default rendering.
- Declined: a live transcript viewer like Claude Code's `/tasks` or Codex's `/subagents` (the owner does not watch; the session id is enough), and a bell or system notification on completion (a matter for pi as a whole).
- Limits: "last action" is the last tool call issued, not necessarily the one executing when a turn issues several; turns count a failed attempt; a line is about 150 characters.

### Removed and declined earlier

Removed chain mode on 2026-11-11: zero uses in 39 recorded sessions (15 subagent calls), no repo instructions using it, and passing one report straight to the next agent bypassed the orchestrator's verification, another mechanism replacing judgement; the orchestrator can sequence calls itself. Removed `agentScope`, `confirmProjectAgents` and project-scoped discovery the same day: no project agents or recorded uses exist, and agents are deliberately user-level only.

No resume parameter (decided 2026-11-11). Continuing a finished subagent in its own context was considered and left out: none of the twenty-odd calls that day needed it, since follow-ups went out as a new brief carrying the earlier report, which is also what `expert`'s description asks for; a fresh context does not inherit the first run's assumptions, resuming resends the whole earlier context, and it would be one more parameter with its own questions. The owner can still continue one by hand with `pi --session <id>`. Signs it has become worth adding: briefs that keep saying "continue what you did before", or subagents that often stop to ask about the brief. The fallback's continuation is not this: it is the same task changing model, inside the extension.

### Agents

Agents are bundles of defaults (model, tools, fallback, report format), not roles; the role goes in the brief. Six cover the grid of model tier × tool set, and each file holds its own model, tools and chain. What the files do not say:

- OpenAI comes first for execution because that subscription is the user's own and Claude is the company's; fallbacks go OpenAI → Anthropic API → Claude Code subscription. `reviewer` is Claude Opus so that it is a different family from the workers.
- `researcher` pins `thinking: high` on sol because synthesis is where research quality lives and the input-heavy fetching step gains nothing from a bigger model; pass `model: openai/gpt-6-astra` for decision-critical research. `expert` and `reviewer` pin `high` too (2026-11-11): the local `modelThinkingLevels` table says the same but is not in the repo and does not cover a `model` override to something it does not list. `scout`, `runner` and `worker` leave it to the table.
- Descriptions and bodies are written as capabilities with coding as one example, not as engineering roles: the example's wording (`codebase`, `Key Code`, `git diff` first) made the orchestrator hesitate to send a document or a plan to `scout` or `reviewer`. All six bodies say the report format the brief asks for wins over the body's own (2026-11-11; before that only `scout` and `runner` did).
- Routing: where and how something is done to `scout`, run this and say what happened to `runner`, judgement to `reviewer`. All three have `bash`, so "read-only" is an instruction, not a tool restriction.
- `runner` was `tester` until 2026-11-11. The name said tests while the job is running anything with a mechanical outcome, and its description's "a checklist against a document" got an audit of `AGENTS.md` routed there, which came back shallow where `reviewer`'s the same day was thorough. `checker` and `verifier` were rejected as names because they suggest judging correctness. Merging it into `scout` was tried and undone before it was committed: the description had to cover two jobs, command-running moved from luna to terra, and the problem had been the name.
- `--tools` can name extension tools such as `web_search` directly; pi-web-access's `web_enable` indirection is only for the default declaration. Noted on 2026-11-11 and not acted on: `researcher` has `fetch_content` but not `get_search_content`, while truncated fetch results tell it to page with that tool.
- `planner` was dropped (the orchestrator is the strongest planner available), `worker-heavy` was renamed `expert`, and the example's three workflow prompts were deleted: process (explore → implement → test → review, when to escalate, when to double-review) belongs to skills such as mattpocock/skills `grill-me`, Google's EGM or obra/superpowers, all of which have pi install paths, not to the mechanism.
- Rejected the same day, all for replacing the orchestrator's judgement with a mechanism: a Luna classifier choosing worker vs expert, automatic escalation on a `STATUS: failed` line, tmux panes per subagent (observation is already in the parent TUI, and steering a subagent would bypass the orchestrator).

### Prior art (observed 2026-11-11)

Claude Code is from its documentation and the 2.1.311 binary; the others are from a researcher subagent's reading of source (Codex at `rust-v0.167.1`, the rest at repository head) and were not re-verified.

- Background by default: Claude Code's documentation says "With nothing configured, a subagent that Claude spawns from your main conversation starts in the background"; waiting needs `CLAUDE_CODE_FORK_SUBAGENT=0`; the binary says the `run_in_background` parameter "is not offered" in a terminal, the desktop app or VS Code, while `claude -p` can wait; its Agent tool prompt says "Never fabricate or predict a pending agent's results" and "do NOT sleep, poll".
- Waking on completion: Codex CLI 0.167.1 returns from `spawn_agent` at once but delivers a child's result with `trigger_turn=false`, so a parent that ended its turn is not woken; issue #46120 reports a 3 h 27 min idle parent and runs with 89 and 96 wasted `wait_agent` polls, and an experimental `wake_on_agent_messages` flag (off) was added for it.
- The user stops one task: Claude Code's single stop sends a normal notification with status `killed` and summary "was stopped by user" plus the partial result, and its Escape-stops-all sends one message with `passive: true, priority: "next"` that rides with the next turn; tintinweb wakes the parent with "STOPPED BY THE USER before completion — output is partial; the task was NOT finished"; nicobailon wakes with "Subagent stopped." and, after the user aborts the parent turn, holds later completions with "The user stopped the parent turn. Report these results at the user's next prompt"; OpenCode wakes with `state="cancelled"`; Codex treats an interrupt as a non-final state and sends nothing.

### Costs

Measured in the main session of 2026-11-11 (`anthropic/claude-fable-5-2`, about 210K tokens of context at the end): 62 requests cost $6.87, $0.11 on average. A short request reading 167K tokens from cache cost $0.066, so the extra reply per dispatch is about $0.06 at that size and less in a smaller session. pi's `cacheWarming` defaults to `idle`: it refreshed the cache 10 times that evening for $0.28, roughly every 4.5 minutes at $0.03 each (cache read at about $0.20 per million), and by pi's settings documentation does so for up to 30 minutes between runs; after that the next request rewrites the context at $10 per million, about $2. A background task that runs longer than 30 minutes with no other request therefore makes its wake expensive once; the longest that day ran 23 minutes. By the documentation, warming continues through an active run, so a foreground call did not have that limit; this was not measured. Report length matters more than any of this: the two research reports were about 14K and 15K tokens, their wake requests cost $0.23 and $0.29, and every later request carried them. Widget, `/task`, folded rendering and `task-record` entries add nothing to the model's context.

### Testing

- Type check: `tsc -p` on a tsconfig kept outside the repo (its paths name the Homebrew Cellar version) with `strict`, `moduleResolution: bundler` and `allowImportingTsExtensions`, including the three files. The `paths` that matter: `@earendil-works/pi-coding-agent` to its `dist/index.d.ts`, `@earendil-works/pi-ai` to `dist/core/extensions/pi-ai-extension-view.d.ts` (the view extensions see, with `StringEnum` and TypeBox), everything else to the package's `node_modules`. Silent when nothing is wrong on 1.5.1 and 1.5.2, and confirmed to fail on a deliberately wrong file.
- Headless: `pi --mode json -p` with Haiku as the main model told to call the tool, reading `tool_execution_end`; and a child started the way the extension starts one (`PI_SUBAGENT=<agent> pi --mode json -p --model subagent/<agent> …`).
- TUI: pi in its own tmux server (`tmux -L <name>`), Haiku as the main model, a scratch working directory and session directory, driven with `send-keys`. Whether the main session woke is read from the session file as the number of assistant messages, not from the screen.
